Chapter 5

Governance: From Stochastic to Deterministic Agentic Development

Speed is the easy part. The hard part is who is accountable, what an agent can actually do, and how you prove what happened. Treat governance as engineering — not policy — across five layers and a spectrum.

⚖️ The Governance Challenge

The moment an agent writes production code, every CIO, CISO, and auditor asks the same three questions: who is accountable, what can the agent actually do, and how do we prove what happened? Fewer than 1% of organizations have fully operationalized responsible-AI practices, and Gartner expects 40%+ of agentic-AI projects to be cancelled by 2027 — often for inadequate risk controls. This chapter answers those questions with engineering, not folklore.

1 The Stochastic-to-Deterministic Spectrum

Every part of an agentic system sits somewhere between pure stochasticity and pure determinism. The goal of governance engineering: push consequential actions toward the deterministic end, and leave only the creative work in the stochastic middle. Click each band to explore.

◀ Stochastic — same input, different output Deterministic — same input, same output ▶

Pick a band. The principle: the higher the blast radius of an action, the further toward the deterministic end it must live. Drafting a memo? Stochastic is fine. Running a production migration? Deterministic procedure under explicit human approval.

2 Five Governance Layers

The layers that turn the spectrum principle into a working system. Click each to expand — explore all five to unlock an achievement.

📜

Layer 1 — Instruction Hierarchy

Where determinism begins: the context window

Three tiers narrow the model's distribution in GitHub Copilot. Tier 1 global ambient rules in .github/copilot-instructions.md — 10–15 imperative non-negotiables. Tier 2 scoped instructions under .github/instructions/ with an applyTo glob — the most underused governance lever. Tier 3 .memory.md treated like code: versioned, reviewed, persisted across sessions. (The equivalent in Claude Code is a root CLAUDE.md plus nested CLAUDE.md files.)

Tier 1: global Tier 2: scoped Tier 3: memory Short · imperative · scoped
🪝

Layer 2 — Hooks

Enforcement at the edge: where governance becomes executable

Instructions tell the model what is expected; hooks make it enforceable. In GitHub Copilot, hooks live under .github/hooks/ and fire on a defined event; a non-zero exit code blocks the action before it runs. Scaled up, agentic workflows in .github/workflows/ pin an entire pipeline — triggers, least-privilege permissions, allowed tools, human gates — into a compiled, version-controlled definition (.lock.yml). (The equivalent in Claude Code is hooks declared in .claude/settings.json with explicit events like PreToolUse.)

.github/hooks/ .github/workflows/ Agentic workflows Least-privilege
📐

Layer 3 — Policy-as-Code

Rules that outlive a prompt, at organizational scale

Hooks are local; policies live in a registry and are inherited everywhere automatically. OPA/Rego expresses rules like "no agent may write to /etc" or "only the release agent may call az deployment create." Good policies are declarative, testable, auditable, and versioned. They map directly onto NIST AI RMF, ISO 42001 Annex A, and the Microsoft Responsible AI Standard.

OPA / Rego Declarative Testable in CI Signed & versioned
🔀

Layer 4 — Parallel Agents

Determinism through scope, not timing

Parallelism is the largest throughput multiplier — and the largest source of non-determinism (race conditions where the racers are LLMs). Three rules tame it: (1) parallelize only on provably disjoint scopes; (2) make shared-state writes idempotent so re-runs are safe; (3) coordinate via durable artifacts in the file system, never via volatile model memory.

Disjoint scopes Idempotency File-mediated handoff
🧾

Layer 5 — The Audit Trail

Making every action explainable after the fact

The deterministic shadow of a probabilistic system — the unified record of every prompt, tool call, retrieved document, policy decision, human approval, and model output. Three properties separate useful from useless: an unbroken causal chain, attributable identity (Entra Agent ID, IAM role, OAuth principal), and tamper-evident storage. It's not insurance — it's the data fabric that makes the system safer over time.

Causal chain Attributable identity Tamper-evident OpenTelemetry

3 Decision Boundaries

Policy-as-code draws the explicit lines between what an agent may do autonomously, what needs a human, and what is forbidden outright. Every action maps to exactly one tier — and the mapping is itself reviewed and audited.

Tier 0

Forbidden — no agent, ever

Deleting production data; pushing directly to main; calling external services with customer PII without explicit redaction.

Tier 1

Human approval required

Agent prepares; a named human approves before execution. Production deploy, schema migration, a refund above a threshold.

Tier 2

Logged and reviewable

Agent acts; a human reviews after the fact. Opening a draft PR, posting an internal summary, creating a non-prod resource.

Tier 3

Fully autonomous

Agent acts; no human review unless an incident is raised. Lint fixes, dependency updates within an approved range, internal docs.

4 Anchoring to External Frameworks

The five layers are the implementation surface for whichever framework an enterprise has chosen. Reassuringly, the frameworks agree more than they disagree.

🇺🇸

NIST AI RMF — Govern, Map, Measure, Manage

Instructions encode Govern & Map; hooks and policy-as-code implement Manage; evaluation, red-teaming and the audit trail implement Measure.

📋

ISO/IEC 42001

An AI Management System standard analogous to ISO 27001 — turns the playbook into a certifiable structure increasingly required in procurement.

🇪🇺

EU AI Act

High-risk obligations apply from 2 Dec 2027 (Digital Omnibus); most other provisions from 2 Aug 2026. Articles 12–17 translate almost line-for-line into these controls. Penalties up to €35M or 7% of global turnover.

🟦

Microsoft Responsible AI Standard v2 — Discover, Protect, Govern

Discover ≈ evaluation & red-teaming; Protect ≈ runtime guardrails & content safety; Govern ≈ observability, audit, and compliance integration.

🛡️

OWASP Top 10 for LLM Apps & MITRE ATLAS

Engineering-grade threat models for prompt injection, insecure output handling, training-data poisoning, and over-permissioned agents.
