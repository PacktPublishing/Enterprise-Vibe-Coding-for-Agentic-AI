Loop Engineering

Stop operating the tool one prompt at a time. Design the loop that operates it for you — a self-running delivery engine that carries a feature from a filed issue to a governed merge, then ships the next one on the very same rails.

1 From Prompting to Engineering the Loop

Primitives are the vocabulary, RPI is the grammar, governance is the law — and the loop is the running program. The expensive part of agentic work isn't generating code; it's re-establishing context at every hand-off. A loop is a machine for making review and accountability cheap and consistent, because it builds them in rather than bolting them on.

2 Anatomy of a Delivery Loop

Every delivery loop is made of the same eight stages, labeled P0–P8 so they can be referenced from primitives, dashboards, and audits. Each stage is really a primitive, an RPI phase, or a governance control wearing a different hat — and none of them mention the feature being built. Click a stage to open it.

Issue-agnostic by design: build the loop once, and every future issue rides the same rails.

3 Worked Example — A Trip Planner for an Airline

Two worlds, kept clean: the passenger is the airline's customer who will one day chat on /book — they never see GitHub. The engineering team uses loop engineering to build that planner. The passenger's chat is the product; the loop is how the product gets made. Follow issue #2194 end-to-end — click each stage.

What it shipped: an accessible chat entry on /book, a slot-filling orchestrator wired to the itinerary + fares APIs, deterministic ranking with rationale, 30-minute persisted state, timeout fallbacks, analytics, and integration + contract tests.

What it cost you: approve the plan, click merge. Six build slices, a CI failure, and a review comment were all absorbed by the loop with unbroken context — and because no .github artifact mentions "trip planner," the same loop carries issue #2195 (seat selection) tomorrow, unchanged.

4 Bounding the Loop

Autonomy without bounds is a liability, not a feature. A production loop must be governed exactly as Chapter 5 describes — with the controls encoded, not assumed.

🧯
Continuation limits
Autopilot runs under a cap (--max-autopilot-continues N). A confused loop must never burn tokens indefinitely.
🚦
Dispatch throttling
Cap how many loops start per cycle (MAX_STARTS) so a backlog can't spawn dozens of concurrent agents.
🔒
Idempotent triggering
Mark an issue loop-started before dispatching, so overlapping cron runs never double-start work.
🔌
Least-privilege MCP
Read CI logs and write to the thread — never hold write access to secrets or production.
🛡️
Hard governance gates
Auth, payments, PII, production always require explicit human authorization, regardless of how green CI is.
📊
Observability
Instrument lead time, defect escape rate, rollback frequency, review load. Speed only counts when trust stays green.

5 Anti-Patterns

A few failure modes recur often enough to name.

❓
No done-condition
If "done" isn't machine-checkable, the loop stops too early or never stops. Wire criteria to a hard gate.
♾️
The unbounded loop
No continuation cap, no dispatch throttle. Works in a demo, bankrupts you at scale.
🌫️
The fuzzy issue
"Make the planner better" has no checkable contract. The issue template is a primitive, not a formality.
🧪
Verification as afterthought
If tests aren't part of the loop, quality depends on someone remembering to ask.
🔀
Product ≠ delivery loop
The passenger's chat is not a trigger for the build-time loop. Keep the two cleanly separated.
⚠️
Ungoverned autonomy
Letting the loop touch auth or payments without a gate trades speed for an incident. Bound it.

6 Knowledge Check

Q1: What is the core shift that loop engineering demands?

Writing longer, more detailed prompts for each task
Designing the loop that prompts the agent, instead of prompting the agent yourself
Replacing all human review with automated approvals

Q2: Why does the done-condition job refuse to pass while any - [ ] remains?

To slow the loop down so humans can catch up
So the loop physically cannot declare itself finished before every acceptance criterion has evidence
Because GitHub Actions requires all checkboxes to be checked

Q3: In the loop, what is a red CI run or a review comment?

An interruption that requires a human to re-start the conversation
A signal to abandon the branch and open a fresh issue
The next input to the loop — the agent diagnoses, patches, and continues without a re-prompt
